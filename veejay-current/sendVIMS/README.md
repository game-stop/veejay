# veejay-puredata

**veejay-puredata** packages the `sendVIMS` Pure Data external for controlling a VeeJay backend through
the VIMS protocol.

It is intended for live patches, hardware/control surfaces, installations, and
automation where Pure Data needs to trigger VeeJay events and consume the
backend's periodic status stream.

## Features

- Connect Pure Data directly to a running VeeJay backend.
- Send fire-and-forget VIMS events from Pd messages.
- Receive the periodic VeeJay status packet as a Pd list.
- Use readable Pd selectors generated from the current VIMS definitions.
- Use convenient live-performance aliases such as `play`, `stop`, `speed`,
  `frame`, and `sample`.
- Address supported VIMS event ports directly with `pNNN` messages.
- Reconnect without recreating the Pd object.
- Keep the Pd command vocabulary synchronized with the backend through
  `parse-vims.pl`.
- Inspect supported aliases directly from Pure Data.
- Use the supplied help patch for status-token mapping and command examples.

## Protocol model

`sendVIMS` deliberately implements a small, predictable subset of VIMS:

```text
Pure Data -> VeeJay
    fire-and-forget VIMS events

VeeJay -> Pure Data
    periodic backend status list
```

It does **not** implement the interactive GUI/query protocol used by commands
that return variable payloads on the command socket.

This keeps the external useful for real-time control without turning it into a
second full VeeJay client implementation.

## Requirements

- Pure Data development headers
- POSIX threads (`pthreads`)
- A `vims.h` matching the VeeJay backend being controlled
- A working VeeJay backend

Keeping `vims.h` synchronized with the backend is important because the
generated Pd aliases are derived directly from the VIMS event definitions.

## Regenerating VIMS aliases

Copy the current backend VIMS header into the `sendVIMS` source directory:

```sh
cp /path/to/vims.h .
```

Then regenerate the selector table:

```sh
./parse-vims.pl vims.h > selectors.h
```

`selectors.h` contains the Pd aliases for supported VIMS events together with
common live-use shortcuts.

Canonical aliases are generated by:

1. removing the `VIMS_` prefix;
2. converting the name to lowercase;
3. replacing underscores with dots.

For example:

```text
VIMS_VIDEO_PLAY_FORWARD -> video.play.forward
VIMS_AUDIO_BEAT_TOGGLE  -> audio.beat.toggle
```

This makes VIMS commands natural to use inside Pd patches.

## Building

Configure the project:

```sh
./configure --prefix=/usr/local
```

Build it:

```sh
make
```

Install it:

```sh
sudo make install
```

A typical installation provides:

```text
/usr/local/lib/pd/extra/sendVIMS.pd_linux
/usr/local/lib/pd/doc/5.reference/help-sendVIMS.pd
```

The exact paths depend on the selected `--prefix` and Pure Data installation.

## Starting VeeJay and Pure Data

Start a VeeJay backend first, for example:

```sh
veejay -p 3490 video.avi
```

Then start Pure Data with the external directory in its search path:

```sh
pd -path /usr/local/lib/pd/extra
```

or from the sendVIMS folder:

```sh
pd -path . -lib sendVIMS -open help-sendVIMS.pd
```


Create a `sendVIMS` object:

```text
[sendVIMS localhost 3490]
```

The first argument is the VeeJay host and the second is the VIMS port.

## Connection control

The connection can also be controlled explicitly from the patch:

```text
[connect localhost 3490(
[disconnect(
[reconnect(
```

This is useful when restarting a backend during development or reconnecting a
live installation without rebuilding the Pd patch.

## Sending VIMS commands

Readable aliases can be sent directly to the object.

Examples:

```text
[play(
[stop(
[speed 2(
[frame 1000(
[sample 3(
[beat.toggle(
[sync.mode 3(
[mix.crossfade 50(
```

Long-form generated aliases can also be used:

```text
[video.play.forward(
[audio.beat.toggle(
```

To print the aliases supported by the current build:

```text
[aliases(
```

or:

```text
[commands(
```

Both commands print the supported Pd-side VIMS vocabulary.

## Raw VIMS event ports

Supported event IDs may also be addressed using the `pNNN` form.

For example:

```text
[p010(
```

is equivalent to the corresponding generated selector and convenience alias,
such as:

```text
[video.play.forward(
[play(
```

Raw event-port access is useful when working directly from the VIMS protocol
documentation or when generating Pd messages programmatically.

## Query commands and VIMS 400–499

VIMS IDs in the `400..499` range are intentionally **not exposed** by
`sendVIMS`.

These commands can return variable-size command-socket payloads such as:

- sample lists;
- stream lists;
- images;
- keyframes;
- effect-chain information;
- VIMS command lists;
- other query/getter responses.

`sendVIMS` does not parse those command-socket replies, so exposing the
commands would create an incomplete and misleading interface.

For the same reason, raw messages such as:

```text
[p400(
```

through:

```text
[p499(
```

are blocked.

Use a full VeeJay client for commands that require request/reply handling.

## Status output

The outlet emits one Pd list for every backend status packet received.

The current VeeJay status packet contains **133 floats**, indexed from `0`
through `132`.

For patching, prefer list operations rather than a giant fixed-width `unpack`.
For example:

```text
[sendVIMS localhost 3490]
|
[list length]
```

and:

```text
[sendVIMS localhost 3490]
|
[list split ...]
```

This is easier to maintain when selecting only the status fields needed by a
patch.

Open:

```text
help-sendVIMS.pd
```

for:

- the current per-token status map;
- live `list split` examples;
- VIMS command examples;
- command argument documentation derived from the VeeJay event definitions.

## Typical uses

`sendVIMS` is particularly useful for:

- custom Pure Data control surfaces;
- MIDI/OSC-to-VeeJay patches;
- generative or algorithmic VJ control;
- sensor-driven installations;
- beat- or audio-reactive control logic;
- hardware controllers;
- show automation;
- external sequencing of VeeJay events;
- monitoring selected backend status values.

Pure Data remains responsible for the higher-level patch logic while VeeJay
performs the real-time video processing.

## Compatibility

`sendVIMS` is intentionally coupled to the VeeJay VIMS definitions.

When updating VeeJay, regenerate `selectors.h` from the matching `vims.h`
before rebuilding the external.

The periodic status layout is similarly backend-version dependent. If the
VeeJay status-token layout changes, update patches that depend on fixed token
positions and keep `help-sendVIMS.pd` synchronized with the backend.

## Scope

`sendVIMS` is a lightweight control bridge, not a replacement for a full
VeeJay client.

It is designed to do two things well:

1. send real-time VIMS events from Pure Data;
2. expose the VeeJay periodic status stream to Pure Data.

That narrow scope keeps the external simple and well suited to live patches,
automation, and custom control systems.
